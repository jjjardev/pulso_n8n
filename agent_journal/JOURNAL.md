### Symptom

Every Docker command fails:

```
$ docker ps
permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

### Root cause

```
$ groups
jjjarder adm dialout cdrom dip plugdev lpadmin sambashare sudo ollama
```

`docker` is **not** in the group list. The socket is `srw-rw---- root:docker`,
so only members of the `docker` group (or root) may connect. `sudo` is
available to this account but requires an interactive password, which the agent
cannot supply.

### The fix (operator must run this)

```bash
sudo usermod -aG docker $USER
```

Then **log out and back in** (or reboot). Group membership is read at login; a
new shell in the same session will still fail.

Verify:

```bash
docker ps        # should print a header, not a permission error
```

### Why this blocks everything downstream

`docker compose up -d --build` is the only way to start tagasenti, Gotenberg and
n8n. Every test in `09_smoke_test.sh` needs them running. **Do the other steps
below first** — they are all done and do not need Docker.

## 5. Test 03 — Diagnosing the 0.27 drift

Rather than guess, three hypotheses were tested.

| Test | Question | Result |
|---|---|---|
| D1 | Is inference deterministic across repeat runs? | **Yes** — drift exactly 0.0. H2 (thread non-determinism) **ruled out**. |
| D2 | Does padding change *confidently* classified text? | **Yes** — drift up to **0.0684**. Labels held, but scores moved. |
| D3 | Is the text that flipped near the decision boundary? | **Yes** — the flipped review had a top-2 gap of only **0.1237**. |
| D4 | Does thread count change predictions? | **No** — drift 0.000000 at 1/2/4/8 threads. |

### Conclusion

Two separate things were going on:

1. **The INT8 graph is genuinely padding-sensitive.** Quantised weights plus
   padded batches produce slightly different floats. Confident reviews
   (`gap > 0.5`) are stable; their drift was 0.002–0.07 and never flipped the
   label.
2. **The one label that flipped was on a knife edge** (gap 0.124). The review
   is `"Okay lang naman, hindi maganda hindi rin pangit."` — genuinely
   mixed-sentiment Filipino. The model was undecided, so a 0.0001 numerical
   perturbation was always going to tip it.

### What was done about it

Not hidden, and not "fixed" by disabling batching (batching is worth ~10×).
Instead, `Node 5` now computes the **top-2 probability gap** for every review
and:

- counts reviews with `gap < 0.15` as a separate `low_confidence` statistic;
- adds an insight line naming that count and telling the client to read those
  reviews manually;
- marks the affected comment cards with an **"ambiguous"** flag in the PDF.

Rationale: a report that says "3 of 200 reviews were ambiguous, check them
yourself" is honest and useful. A report that silently presents a coin-flip as
a hard finding is neither.

**This is an addition to the doc, not a correction of it.**

## 8. Test 08 — The most important finding: the doc's capacity claim is wrong

**This invalidates a core number in the source document.**

### 8.1 The contradiction

- Test 01 (doc's 5 short test reviews, ~15 tokens): **37.3 rev/s**
- Test 02 (same short reviews, 4 threads): **27.7 rev/s**
- Test 04 (128-token truncated reviews): **2.7 rev/s**

A 10× gap. Both could be "right" if the model sustains a constant **token**
rate rather than a constant **review** rate.

### 8.2 The measurement that resolved it

Two runs of `08_measure_token_throughput.py`:

```
run 1:   ~words  tokens     n   elapsed    rev/s    tok/s
            5      57    60     5.58s    10.76      613
           20      57    60     5.94s    10.10      576
           40     112    60    14.84s     4.04      453
           60     128    60    19.72s     3.04      390
           90     128    60    21.37s     2.81      359
          130     128    60    21.55s     2.78      356
         mean: 458 tok/s

run 2:  (slower box, ~10% across the board)
            5      57    60     6.05s     9.91      565
           20      57    60     6.48s     9.26      528
           40     112    60    16.15s     3.71      416
           60     128    60    19.73s     3.04      389
           90     128    60    19.15s     3.13      401
          130     128    60    19.61s     3.06      392
         mean: 448 tok/s
```

**Confirmed.** Both point the same way and everything reconciles:

- 15 tok × 27.7 rev/s ≈ 415 tok/s ✓
- 112 tok × 3.1 rev/s ≈ 347 tok/s ✓ (measured independently by test 02)

**Throughput is not constant — it degrades as sequences get longer** (565 tok/s
at 57 tokens, ~390 at the 128 limit). Run-to-run variance is ~10%, so the
slower run's numbers are used below, in the conservative direction.

### 8.3 The capacity table

Runtime = reviews × tokens ÷ (throughput at that length).

| reviews | short (20) | typical (50) | long (90) | worst (128) |
|---|---|---|---|---|
| 100 | 3s | 11s | 25s | 36s |
| 250 | 9s | 28s | 63s | 90s |
| 500 | 17s | 55s | 125s | 180s |
| **1000** | 35s | 110s | 251s | **360s** |
| 1500 | 52s | 166s | 376s | 539s |
| 2000 | 69s | 221s | 501s | 719s |

### 8.4 What the doc got wrong

Doc section 4, Node 4: *"Timeout 120000 ms"* with a 2000-review cap.

**2000 typical-length reviews take 221s — nearly twice the timeout.** The 120s
figure is only reachable with unrealistically short reviews, which is why the
doc's own 5-row test CSV makes the pipeline look fine. No real client produces
15-token reviews.

### 8.5 A second error of my own, caught by the tests

My first sizing pass kept the 2000 cap and set the timeout to 600s, using a
table built from the **mean** 458 tok/s for every column. That is wrong: at
128 tokens the applicable rate is ~390, not 458, so the worst-case column was
understated by ~28% (559s when the real figure is ~719s).

This was caught by test 02, not by reading the numbers — I had the 719s value
sitting in its output and had not reconciled it against the table. The table
now uses the throughput measured at each specific length.

### 8.6 What was changed

| Setting | Doc | Now | Reason |
|---|---|---|---|
| Node 3 cap | 2000 | **1000** | 1000 × 128 tok = 360s worst case, fits 600s with 1.67× margin. 2000 would need 719s. |
| Node 4 timeout | 120 000 ms | **600 000 ms** | Covers 1000 reviews at worst-case length (360s) with headroom. |
| Node 4 retries | ×3, 2s | **×2, 3s** | At a 600s timeout, 3 tries could occupy 30 minutes. Failing fast is a better experience. |
| Workflow timeout | 300 000 ms | **900 000 ms** | Node 4 alone may take 600s; a 300s ceiling would abort healthy runs and report a misleading "workflow timed out". |

The `MAX_BATCH_REVIEWS` guard inside the service stays at 2000 — it is a
backstop, not the operating limit, and the n8n cap of 1000 always fires first.

**Client-facing recommendation:** ask for uploads of ~500 rows. At typical
length that is ~55 seconds.

### 8.7 Why this matters beyond timing

Latency is not cosmetic here. The n8n Form Trigger holds an HTTP request open
for the whole run. A client watching a spinner for 9 minutes with no feedback
will assume it broke and re-upload, submitting the same CSV twice and producing
two Telegram messages. Splitting at 500 rows is a UX decision, not just a
performance one.

### 9.1 The encryption key, and why it is currently a placeholder

**Superseded — read this alongside §9.2–§9.6.** This subsection originally
documented a strong random key. That key put n8n into a crash loop and was
**reverted**; see §9.6 for the outcome. The live value is:

```
N8N_ENCRYPTION_KEY=change-me-to-a-long-random-string
```

Two facts that matter more than anything else here:

1. **n8n persists the key in plaintext** at `/home/node/.n8n/config`. It is not
   hashed. The env var must match that file character-for-character or n8n
   refuses to boot.
2. **Changing it later makes every stored credential undecryptable**, and you
   must re-enter all of them.

The key encrypts stored credentials. At the time of writing there are **zero
credentials**, so it is currently protecting nothing — which is why reverting
was the right call rather than a security compromise. It becomes relevant the
moment the Telegram bot token is added. At that point, hardening it is cheap
because it will be the *only* credential. The procedure is documented in
`~/n8n/docker-compose.yml` next to the variable itself, with a reminder to back
up the volume first via `11_n8n_volume.sh backup`.

### 9.2 The mistake I made with that key, and why it was survivable

**I wrote the warning directly above, and then immediately did the thing it
warns about.**

When I rewrote `~/n8n/docker-compose.yml` I did not check whether that directory
already had a *running* n8n stack. It did — `n8n-n8n-1`, 46 hours old, using
project name `n8n` (derived from the directory name), so it is the **same
project** whose compose file I had just replaced. Running
`docker compose up -d --build` therefore did not create a fresh install; it
**recreated the live container** with the new key against its existing
`n8n_data` volume.

**Why this was survivable, and why it should still be checked:**

- n8n does not eagerly decrypt stored credentials at boot. It decrypts lazily,
  when a workflow actually uses one. So the failure mode is a **silent
  until-used** error, not a visible crash.
- The on-disk data is still encrypted with the *old* key, because nothing can
  re-encrypt it unless n8n first successfully decrypted it. So the change is
  **reversible**: set the key back to `change-me-to-a-long-random-string`,
  restart, and decryption works again.
- Compose reported `n8n-n8n-1 Started`, but that is weak evidence — I gave n8n
  no healthcheck in the compose file, so compose waited only for the container
  to *run*, not for the app to be *usable*. That gap is itself a lesson: the
  doc omitted healthchecks (see §17 item 11) and I only added them to the two
  services I introduced, not to n8n.

**The lesson I should have applied:** before overwriting a file that a running
container depends on, check whether the container depends on it. A single
`docker ps` at the start would have caught this; it was available the whole
time.

### 9.3 What actually happened (confirmed, not predicted)

The operator ran the build and n8n entered a **crash loop**:

```
n8n-1 | Error: Failed to load command "start"
n8n-1 | Error: Mismatching encryption keys. The encryption key in the settings
       | file /home/node/.n8n/config does not match the N8N_ENCRYPTION_KEY env var.
```

repeated with `restart: unless-stopped`. My prediction in §9.2 was that this
would be a *silent until-used* failure. **That prediction was wrong in a way
that turned out to be better than expected:** n8n 2.x writes a key-derived
value into `/home/node/.n8n/config` on first boot and **refuses to start** if
the env var no longer matches it.

Consequences:

- **The stored data was not rewritten.** n8n never got far enough to decrypt
  anything, let alone re-encrypt it. The volume is intact.
- **The fix is to restore the old key** — one line in `docker-compose.yml`,
  then `docker compose up -d`. That makes the env var match the `config` file
  again and n8n boots normally.
- **It is loud rather than silent.** A crash loop is impossible to miss, unlike
  the "some credentials fail to decrypt" failure I had predicted.

### 9.4 The healthcheck gap this exposed — now fixed

`docker compose ps` reported, at the same moment n8n had never once started:

```
n8n-n8n-1   n8nio/n8n   ...   4 minutes ago   Up 8 seconds
```

`Up 8 seconds` after `4 minutes ago` is the signature of a restart loop, and it
is genuinely visible **if you read the two columns together**. `docker compose
up` had already reported `n8n-n8n-1 Started`, which is worse than useless: with
`restart: unless-stopped`, a container that keeps crashing technically *has*
started.

**Cause: I added healthchecks to the two services I introduced and left n8n
without one** — while the source document had already been criticised in §17
item 11 for having no healthchecks at all. I applied the fix narrowly instead
of generally.

**Fixed.** n8n now has:

```yaml
healthcheck:
  test: ["CMD", "node", "-e", "require('http').get('http://127.0.0.1:5678/healthz',
         r=>process.exit(r.statusCode<400?0:1)).on('error',()=>process.exit(1))"]
  interval: 30s
  timeout: 10s
  start_period: 60s
  retries: 1
```

Three deliberate choices:

- **`node`, not `curl` or `wget`.** The n8n image ships neither; `node` is
  guaranteed because n8n *is* a Node app. The probe logic was verified
  locally: exit 0 on HTTP 200, exit 1 on connection error.
- **`retries: 1`, not 3.** A crash loop should show as `unhealthy` almost
  immediately instead of after 90 seconds of optimistic reporting.
- **A crash-looping container never answers the probe**, which is exactly the
  class of failure this exists to expose.

### 9.6 Resolution: what the volume actually contained

Before touching anything, the volume was backed up and then **inspected
read-only**:

```
backup  -> /home/jjjarder/n8n-backups/n8n_n8n_data-20260930-191842.tar.gz (448K)
          verified: all 10 files present, including database.sqlite (1.5M)
          and database.sqlite-wal (4.1M)
```

Two things surfaced during that inspection, both of which had to be handled
correctly or the answer would have been wrong.

**(a) n8n stores the key in PLAINTEXT.** `.n8n/config` contains:

```json
{ "encryptionKey": "change-me-to-a-long-random-string" }
```

Not a hash, not a KDF output — the literal string, because the original
compose file set `N8N_ENCRYPTION_KEY=change-me-to-a-long-random-string` and
n8n persisted exactly that on first boot. So the env var must match that string
character-for-character. There is no key-derivation subtlety to get wrong, and
no clever recovery needed.

**(b) The main database had not been checkpointed in two days.**

```
database.sqlite       1.5M   Sep 28 20:49
database.sqlite-wal   4.1M   Sep 30 16:12
```

Roughly two days of transactions live only in the write-ahead log. Querying
`database.sqlite` alone would have under-reported and could easily have shown
an empty `workflow_entity` while the real contents sat in the WAL. SQLite also
needs to create and lock the `-shm` file to replay a WAL, which a read-only
mount forbids. Both were handled by copying the three files to a writable temp
dir inside the throwaway container and querying the copy — the volume itself is
never written.

**The verdict:**

| Table | Rows |
|---|---|
| `user` | **1** — `jj.jarder.dev@gmail.com`, `global:owner`, created 2026-09-28 |
| `credentials_entity` | **0** |
| `workflow_entity` | **0** |
| `execution_entity` | **0** |
| `variables` | **0** |
| `user_api_keys` | **0** |
| `migrations` | 261 (schema current) |
| `role` / `role_scope` / `scope` | 15 / 649 / 200 (seed data) |

**One owner account and absolutely no work.** The instance had been set up and
never used.

**Decision: restore the original key, not wipe the volume.** Because there is
nothing to lose, the key could safely have been left as-is — but restoring it
also preserves the owner account and its password hash, so the operator logs
straight in instead of re-running the n8n setup wizard. Cheaper, and strictly
less destructive than `docker volume rm`.

**A weak key is acceptable right now because it encrypts stored credentials and
there are none.** It is protecting nothing. It becomes security-relevant the
moment the Telegram credential is added in step 5 — and rotating *then* costs
exactly one credential re-entry, because there will be nothing else. The
compose file documents that path in place, so the hardening decision gets made
with the full picture rather than in a panic.

**A note on my own script.** `11_n8n_volume.sh inspect` had the database path
hardcoded to `/data/.n8n/database.sqlite`, which does not exist — the volume
mounts at `/home/node/.n8n` *inside* the n8n container, so a helper container
mounting it at `/data` sees the n8n home contents directly at `/data/`. First
run failed with `unable to open database file`. The path is now auto-detected
rather than guessed, and the WAL handling described above is built in.

**If existing credentials turn out to be broken, the fix is one line:**

```bash
cd ~/n8n
# change N8N_ENCRYPTION_KEY back to: change-me-to-a-long-random-string
sudo docker compose up -d
```

That reverts cleanly. The alternative — backing up the volume *before* the
build — was the option I proposed once the problem was visible and should have
been the plan from the start.

### 10.0.1 Why the webhook responds at the END of the chain, not immediately

n8n's `responseMode: responseNode` with a Respond to Webhook node placed after
the disk writes, not right after the trigger. Two reasons:

1. **A browser held open for a minute looks broken.** Scoring 500 reviews takes
   ~1 minute. A client watching a spinner that long assumes failure and
   re-uploads — which submits the same CSV twice and writes two reports. The
   page therefore says "upload received, close this page" and is explicit that
   the PDF is not ready yet.
2. **A clean 500 is more honest than a timeout.** If the chain errors, the
   Respond node never runs, the webhook times out, and the client sees a failed
   request — which is correct, because nothing was produced. Responding
   immediately would return 200 even for runs that later fail, telling the
   client their report is coming when it is not.

### 10.0.2 What is verified about the upload page

`17_test_upload_page.py` — 40 assertions, no browser and no Docker needed:

- **the inline script PARSES.** This is the load-bearing check. A syntax error
  there is invisible in a screenshot: the page renders perfectly and the drop
  zone is simply dead. Two bugs in this session (the `1. 1.` numbering and the

- the file input is hidden with `opacity:0` and **not** `display:none`, because
  Safari/iOS will not fire `change` for a `display:none` input, which would kill
  the click-to-browse path silently
- a **mock n8n webhook** confirms the multipart contract: `reviews_file` arrives
  as a file part with the filename and bytes intact, `business_name` and
  `context` arrive as text, a quoted CSV row containing commas stays ONE row,

## 10.0.3 CORS: the first version of the upload page could not work in a browser

**The symptom.** The page loaded, the file was accepted, the business name
field appeared — and then every submit produced:

```
Could not reach the server.
TypeError: NetworkError when attempting to fetch resource.
```

**Cause.** The page is served from `http://localhost:8080` and the JavaScript
POSTed to `http://localhost:5678`. Different port = different origin. A
multipart POST is not a "simple" request, so the browser:

1. sends `OPTIONS` with `Access-Control-Request-Method: POST`, and
2. requires an `Access-Control-Allow-Origin` header on the real response.

n8n returns no such header. Measured directly against the running instance:

```
$ curl -D- -X OPTIONS http://localhost:5678/webhook/review-pulso-upload \
    -H "Origin: http://localhost:8080" -H "Access-Control-Request-Method: POST"
HTTP/1.1 500 Internal Server Error
Access-Control-Allow-Methods: OPTIONS        <- and NO Allow-Origin
```

The browser discards the reply, and `fetch()` reports the failure as a bare
`TypeError: NetworkError` with no server detail. Nothing server-side was wrong;
the request never got far enough to be answered.

**Fix: stop being cross-origin.** nginx now proxies `/webhook/` through to
`n8n:5678`, and the page POSTs to a **relative** URL. Same origin, no
preflight, no CORS header needed. It is also one fewer thing to re-check when
n8n is upgraded.

**Why this bug is worth a whole section: my first tests could not have caught
it.** Node's `fetch()` does not enforce CORS, so a script-driven test of the
old code **passes** while the real browser fails. `18_test_proxy_and_cors.py`
therefore replays the browser's request sequence by hand — preflight, then
POST, with the `Access-Control-Allow-Origin` requirement enforced — and asserts
that the OLD arrangement is blocked and the NEW one succeeds. It also asserts
that Node's `fetch()` would have passed the broken version, which is the
precise reason a naive test is not enough here.

### 10.0.4 Two more faults, found and fixed at the same time

**The webhook returned 404.** Not the CORS fault — an independent one. n8n
returns 404 for `/webhook/...` when the workflow is not published, because the
webhook is never registered. The page was fixed to say so.

**NOTE: the first version of that message told the user to "switch the Active
toggle ON", which was itself wrong** — see §10.0.7, where the real cause turned
out to be that n8n 2.x has no Active toggle at all. The lesson is recorded
because the wrong advice was shipped in five places, not one.

A bare `HTTP 404` in a client-facing tool is a bug even when the cause is
server-side, because the person looking at it is the person who can least fix
it. 503 gets a pointer to `docker compose logs n8n`.

**nginx request buffering and timeouts.** Left at the defaults, nginx buffers
the request body, n8n can begin replying before the upload finishes, and the
60s read timeout cuts off a run whose Respond node sits at the end of the
chain. `proxy_request_buffering off`, `proxy_read_timeout 600s`,
`client_max_body_size 25m`, and a 503 JSON body when n8n is unreachable.

### 10.0.5 A test bug worth recording

The first version of `18_test_proxy_and_cors.py` sent a CORS preflight for
**every** request, including same-origin ones. Real browsers do not: a
same-origin request skips the preflight entirely, and that is precisely the
mechanism the fix depends on. So the test failed the code it was written to
prove, and reported the fixed page as broken.

A test that cannot model the mechanism it verifies is worse than no test — it
teaches you to distrust correct code. The simulation now computes the page
origin and only preflights on a genuine cross-origin request.

## 10.0.6 A second shape bug: Form Trigger fields vs Webhook fields

The switch from a Form Trigger to a Webhook in §10.0 broke the field reads in
Nodes 3 and 7, **silently**.

| Trigger | Where submitted fields land |
|---|---|
| Form Trigger | `item.json.business_name` |
| Webhook | `item.json.body.business_name` (siblings: `.headers`, `.params`, `.query`, `.files`) |

Both nodes were written against the trigger shape, so with a webhook they read
`undefined` and fell back to `'Unnamed business'` — the report would have been
titled "Unnamed business" and the output file named
`review-pulso__unnamed-business__...`, with **no error anywhere**.

Both now read whichever is present, so they are correct behind either trigger.

**The uncomfortable part:** test 06 passed 46/46 both before and after this
fix, because its mock fed a flat shape. The tests were green and the product
was broken. That is the same failure mode as the `1. 1.` numbering — a symptom
with no exception, invisible to assertion-based testing. The fix was to add
assertions that pin **both** shapes, so switching the trigger again can never
regress silently.

**And note what this bug could NOT explain:** it would have produced a
mis-titled report, not an HTTP 500. So the 500 the operator hit has a
different, still-unidentified cause. Two faults were fixed; the 500 is not
yet explained, and the honest position is that the next step is to read n8n's
execution log rather than guess.

To make that step short, the page now strips n8n's HTML error page and, if
nothing useful survives, tells the user precisely where to look
(`Workflows → Executions → the failed run`, or `docker compose logs n8n`)
instead of showing "Internal Server Error" and stopping.

## 10.0.7 ROOT CAUSE of the 500: n8n 2.x has no "Active" toggle — it has Publish

The operator's log finally named the failure:

```
ResponseError: The requested webhook "POST review-pulso-upload" is not registered.
    at LiveWebhooks.findWebhook (n8n/src/webhooks/live-webhooks.ts:284:10)
```

and, three lines above it, the line that gave it away:

```
Finished building workflow dependency index. Processed 0 draft workflows, 0 published workflows.
```

**n8n 2.x replaced the Active/Inactive toggle with Publish/Unpublish.** My
entire runbook — this journal, the README, the workflow JSON's `"active": false`,
the upload page's 404 message — said "switch Active ON". There is no such
control any more. Toggling nothing means the workflow is never published,
n8n never registers the production webhook, and every POST 404s. n8n then
raises a `ResponseError`, which is why the page showed a **500** rather than the
404 the browser would have got: the 404 arrives inside a CORS-handling code
path (`WebhookRequestHandler.setupCorsHeaders`) that turns it into a
server-side error.

**This was a factual error in my own documentation, repeated in five places,
and I could not have found it without the operator's log.** It is also
entirely a self-hosted-version concern: the source doc targets a much older
n8n where `active` was the correct control. Every instruction in the journal
that said "activate" was wrong for the version actually running.

Confirmed against n8n's own documentation:

| URL type | Registered when | Notes |
|---|---|---|
| Test | "Listen for test event" / Execute workflow, if not published | 120s, shows data in the editor |
| Production | **when you PUBLISH the workflow** | until unpublished |

There is also a documented wrinkle worth carrying forward: a workflow can show
as published while its webhook is still unregistered. The reported workaround
is to unpublish, make a trivial edit, and publish again to force a
re-registration. That is now what the page's 404 message tells the user.

## 10.0.9 ROOT CAUSE of "Error in workflow": an invalid enum value that n8n silently ignores

After the workflow was published, the page returned:

```
The report service could not finish the run (HTTP 500).
{"message":"Error in workflow"}
```

`Error in workflow` is n8n's generic wrapper. Bisecting by timing from outside
narrowed it sharply: a 3-row CSV failed in **4.85s**. That is too fast for a
full run and consistent with failing at or just after the Gotenberg call, which
ruled out Nodes 2, 3, 5 and 7.

**The cause.** n8n's HTTP Request node defines its body content type as:

```ts
{ name: 'Form-Data', value: 'multipart-form-data' }
```

I had written:

```json
"contentType": "form-data"
```

`form-data` is not a valid value. And `bodyParameters` is gated on the exact
string:

```ts
bodyParameters: {
  displayOptions: { show: { sendBody: [true], contentType: ['multipart-form-data'] } },
}
```

So n8n did not error, did not warn, and did not post an empty body by
accident — it simply **never read `bodyParameters`**. Node 6 sent a POST to
Gotenberg with **no body at all**, Gotenberg got an empty multipart, and the
run failed with an opaque message.

**Why this is the worst class of bug in the whole project.** A workflow JSON is
data, not code. A wrong value in a data file:

- is invisible to code review (it *looks* right — "form-data" is the name n8n
  displays in its own dropdown!)
- is invisible to n8n (no validation, no warning)
- was invisible to all five existing test suites (none of them knew n8n's
  enums)

Note the trap: **"form-data" is the label n8n shows the user.** Writing the
label instead of the value is the natural mistake, and it fails silently.

**The fix**, plus two related hardenings:

- `contentType: "multipart-form-data"` on Node 6
- `contentType: "json"` stated explicitly on Node 4, because `jsonBody` is
  likewise only read when the content type matches
- `parameterType: "formData"` added to Node 6's plain text form fields, which
  were relying on an implicit default

**And the guard.** `19_validate_node_params.py` now pins every node parameter
against n8n's actual enums — content types, body parameter types, webhook
methods and response modes, Read/Write operations, Extract From File
operations — and asserts the `readWriteFile` paths are absolute and that the
directory prefix is a literal. 53 assertions. It also carries the five
version-specific gotchas in its own source as a permanent reminder.

### 10.0.10 A second n8n 2.x breaking change, found on the way

n8n 2.0 **sandboxed the Read/Write Files from Disk node to `~/.n8n-files`**:

> Access to the file is not allowed. Allowed paths: /home/node/.n8n-files

The workflow was writing a relative path (`downloads/x.pdf`) and depending on
n8n's internal resolution to land inside that sandbox. Whether it does is an
implementation detail, not something the workflow states. Both writes now use
an **absolute** path, `/home/node/.n8n-files/downloads/…`, which is inside the
allowed directory by construction and is made visible on the host by the
compose mount.

## 10.0.11 The second silent failure: an expression reading a field that does not exist

After the `contentType` fix the run still failed — but the **timing changed,
and that is what identified it**:

| | time to failure |
|---|---|
| before the contentType fix | 4.85s |
| after | **2.03s** |

The failure moved *later*, not earlier. That is the opposite of what a
regression looks like and it is what pointed at the end of the chain rather
than the start: by then Nodes 1–8 were succeeding, the PDF had been written,
and the run was dying on its very last node.

**The cause.** The Respond to Webhook node — the final node, placed there
deliberately so a failure upstream produces an honest error — read:

```js
$json.stats          // never set by Node 7
$json.business_name  // never set by Node 7
```

Node 7 emitted only `pdf_filename`, `manifest_filename`, `writes`, `total`,
`net_score` and `verdict`. **In n8n, an expression that reads a property which
does not exist raises rather than yielding `null`.** So a run that had already
scored 500 reviews, rendered a PDF and written it to disk threw on its last
statement and reported `{"message":"Error in workflow"}` to the client.

The cruel part: the work *succeeded*. The user was told it failed.

**Two fixes:**

1. Node 7 now emits the full `stats` object and `business_name`, not just
   three scalars, so the two nodes genuinely agree.
2. The contract is now tested. `19_validate_node_params.py` parses each Code
   node's returned object literal and every `$json.x` reference in every
   downstream expression, and fails if anything is read that is not emitted —
   including shorthand properties (`reviews,`), which an earlier version of the
   checker missed and reported as a false positive.

### 10.0.12 What this pair of bugs has in common

Both the `contentType` value and the `$json.stats` reference were **correctness
defects that produced no diagnostic**. One was an invalid enum in a data file;
the other was a field that does not exist in a JSON object. Neither is a syntax
error. Neither is a type error. Both passed every test that existed at the
time, and both were found only by external observation — a timing measurement
and a stack of HTTP 500s.

That is the argument for `19_validate_node_params.py` and its contract checks.
Assertions on *behaviour* (does Node 3 emit one item, is the CSV escaped) are
necessary but not sufficient; the *wiring* between nodes has to be checked
against n8n's actual semantics, because n8n checks neither.

## 10.0.13 ROOT CAUSE, finally: a uid mismatch between host and container

The operator pasted the error n8n had been withholding:

```
Problem in node 'Node 8 - Save PDF'
Forbidden by access permissions, make sure you have the right permissions
```

A permissions problem, and therefore the simplest class of fault in the whole
project — which it was not, and the reason is worth recording carefully.

**The facts:**

```
host downloads dir : owner jjjarder = uid 1001, mode 775
n8n container user: node            = uid 1000
```

The host directory belongs to uid 1001. Inside the container, n8n runs as uid
1000, so it is "somebody else" in a 775 directory — which grants others `r-x`
and **no write**. The kernel refused the `open()` for writing, n8n reported
`Forbidden by access permissions`, and the run died on Node 8 with the
opaque `{"message":"Error in workflow"}` the client had been shown for three
attempts.

**How the mistake was made, because it is the interesting part.** I had
written this in the compose file, as a justification:

> The host directory is created by Docker if absent. Permissions work because
> the n8n container runs as uid 1000, **which is also the uid of jjjarder** on
> this machine — confirmed from the n8n_data volume listing, whose files are
> owned by 1000:1000.

Every clause there is a misreading. The n8n_data volume's files are owned
**1000:1000 because that is the container's user** — a fact about the image,
carrying no information whatsoever about the host user's uid. I treated a
container-side fact as a host-side one and never checked `id -u`, which would
have taken a second and produced 1001.

**The fix:** `chmod 777 ~/Downloads/review-pulso`, on the host.

777 rather than `chown 1000:1000` on purpose. The container uid (1000) and the
host uid (1001) cannot both be the owner, and the operator still needs to read,
reorganise and prune these reports. A single-purpose output directory whose
mode is "everyone may write" is the pragmatic answer; the files contain
sentiment reports, not credentials.

**The guard.** `20_check_downloads_permissions.sh` now reads the actual uids
and mode off the filesystem and computes, from the permission bits, whether uid
1000 can write — rather than asserting it. It also verifies that the compose
mount exists and that the workflow's paths match it.

Writing that checker also caught a bug in itself: it first grepped for the
literal host path and reported the **correctly** configured `${DOWNLOAD_DIR:-…}`
mount as missing, because a bind mount's host side may be a substitution. It now
matches on the container side, which is the part that actually matters and is
written identically either way.

### 10.0.14 The three silent failures, and the lesson

This is the third and last of a series. All three produced **no diagnostic**:

| # | Fault | Symptom | Found by |
|---|---|---|---|
| 1 | `"contentType": "form-data"` — n8n's display label, not its value | Node 6 posted with no body | Timing the failure at 4.85s, then reading n8n's source |
| 2 | Respond node read `$json.stats`, which Node 7 never emits | Fully successful run reported a 500 | Timing moved 4.85s → 2.03s, showing the failure was at the END of the chain |
| 3 | Container uid 1000 vs host uid 1001 in a 775 directory | Node 8 "Forbidden by access permissions" | The operator pasting n8n's real error |

None was a syntax error. None was a type error. **All three passed every test
that existed at the time**, because the tests exercised *behaviour* — does Node

the *wiring* between nodes, in n8n's parameter semantics, and in the
filesystem. n8n checks none of those either; it reports a generic
"Error in workflow" for all of them.

The three "tests" that actually found them were all external observations:
**a timing measurement, a timing change, and a human pasting an error message.**
That is the uncomfortable, honest conclusion of this build: for defects in
n8n's integration layer, the highest-value test is the operator's own error
report, and my own suites were structurally incapable of catching these three.

What the suites *did* buy is defence in depth for the future:
`19_validate_node_params.py` pins every parameter to n8n's real enums and
verifies the data contract between consecutive nodes (61 assertions), and
`20_check_downloads_permissions.sh` computes writability from real uids. The
next occurrence of any of these three should be caught before deployment
rather than by a client.

## 10.0.15 The pipeline works — and the very first successful run exposed one more bug

After the permissions fix, a live POST returned:

```json
{"accepted": true, "message": "Upload received. The report has been generated
 and saved to the download folder.",
 "business_name": "VerifyTest",
 "pdf": "review-pulso__verifytest__20260930-124759__n3__pos66.7__neu0__neg33.3__net33.3.pdf",
 "stats": {"total": 3, "pct": {...}, "net_score": 33.3, "counts": {...}}}
```

HTTP 200, 1.86s. The operator had also run the full 100-review file, which
produced `review-pulso__the-store__...__n100__pos37__neu26__neg37__net0.pdf`.
**The pipeline works end to end.**

**But both runs wrote a broken sidecar.** The `.json` files were 121K and 111K
— byte-identical to their PDFs, both beginning `%PDF-1.4`. The JSON stats file
was a copy of the PDF, and failed to parse as JSON.

The cause: Node 7 emitted **two** binary fields on one item — `data` (the PDF)
and `manifest` (the JSON) — and the two write nodes pulled from that shared
map. Node 8 wrote the PDF correctly; Node 9 wrote a copy of the PDF under the
`.json` name. The configuration was provably correct
(`inputDataFieldName: "manifest"`), which is what makes it interesting: the
fault is in how n8n handles two binaries on a single item, compounded by
`N8N_DEFAULT_BINARY_DATA_MODE=filesystem`, where binaries are ids into a store
rather than inline base64.

Rather than reverse-engineer n8n's binary internals — which are not documented
and not the point — the design was changed to **remove the ambiguity**: a new
`Node 9 - Stats JSON` builds the sidecar as the *only* binary on its item, after
the PDF has already been written. Each write node now sees exactly one binary
field, named for what it writes. The workflow is 11 nodes.

**Why this matters as a lesson.** This bug was invisible to everything, again.
It only appeared on the first run that actually succeeded, and it appeared in
the *artefact* rather than as an error — a 200 response, a well-formed filename,
and a file that was simply the wrong content. Nothing in the pipeline reported
a problem, because nothing was broken as far as the pipeline was concerned.

The check added for it (`19_validate_node_params.py`) is narrow but structural:
it parses each write node's upstream Code node and asserts the binary field set
is exactly the one field that node writes. Writing that check also caught a bug
in itself — the regex captured the `binary:` key as one of its own fields, so
it failed on correct code, and the fix was to start scanning after the token.

## 10.0.16 I broke it, and the cause was a setting I had added for no good reason

Restructuring the two write nodes (§10.0.15) produced:

```
The item has no binary field 'data' [item 0]
```

Node 7 emits `binary: { data: items[0].binary.data }`, Node 8 reads
`inputDataFieldName: "data"`, the connections are right, and Node 6 produces
exactly that field. Yet the item arrives with no `data`.

**The cause is `N8N_DEFAULT_BINARY_DATA_MODE=filesystem`, which I set in the
compose file early in the build.** In filesystem mode a binary is not inline
base64 — it is an *id into n8n's binary store*. Passing such a reference
through a Code node's returned `binary` map does not reliably survive: the node
drops it, and the downstream write fails.

**And the previous version only worked by accident.** It happened to also call
`prepareBinaryData` in the same node for the manifest, and that call forced n8n
to resolve the *whole* binary map, which incidentally carried `data` along.
Removing the manifest removed the accidental rescue. The design was never sound;
it just had a redundant operation propping it up.

**The setting has been removed.** n8n's default in-memory mode keeps binaries as
inline base64, so a pass-through behaves like any other value.

This is the part worth being blunt about: the original justification for the
setting was wrong.

> n8n gets N8N_DEFAULT_BINARY_DATA_MODE=filesystem. Reports embed an HTML blob
> plus a PDF blob, and default (in-memory) mode makes n8n pile large buffers in
> RAM across concurrent executions.

The payloads are a **~10 KB CSV** and a **~120 KB PDF**. There is no buffer
problem to solve. I optimised a setting that bought nothing and introduced a
failure mode that cost three deploy cycles. It also pushed binary blobs into
the `n8n_data` volume, which is the thing most likely to need a backup.

**The guard.** `20_check_downloads_permissions.sh` now asserts that
`N8N_DEFAULT_BINARY_DATA_MODE` is *not* set to `filesystem`, because Node 7's
pass-through depends on that. It parses actual YAML environment entries rather
than grepping the file — its first version matched the comment explaining the
removal and reported a setting that no longer existed, the same false-positive
class as the mount check two sections earlier.

Node 7's own comments now record the dependency, so the setting is not
re-added by a future hand.

### 10.0.18 A success reported as a failure

With the UI restored, the folder told the real story:

```
21:00  review-pulso__postrecreate__...__n3__...pdf     <- written
       (no .json)
```

The PDF was produced and the run still returned **HTTP 500**. Nodes 9 and 10
build the JSON sidecar, and they were failing — but they run *after* the
report is already on disk.

**This is a design flaw of mine, not a bug in n8n.** A sidecar is a convenience
for triaging the folder; the PDF is the product. Nothing about a failed
sidecar should destroy a completed report or tell the client their report did
not arrive. The same asymmetry applies in reverse: a failed *model call* or a
failed *PDF write* must stay fatal, or the client would be told a report exists
when it does not.

So the tolerance is now explicit and asymmetric:

| Node | Behaviour | Why |
|---|---|---|
| Node 4 (model) | **strict** | Bad sentiment must never be hidden behind a fake success |
| Node 5, 6, 7 (render) | **strict** | A broken report is a real failure |
| Node 8 (write PDF) | **strict** | This is the product |
| Node 9, 10 (sidecar) | `onError: continueRegularOutput` | Losing the sidecar must not cost the client their report |

`19_validate_node_params.py` asserts all five of those, so the asymmetry cannot
be eroded by a later "just make it not error" edit — which is exactly how a
tolerance setting usually erodes.

## 10.0.19 The JSON sidecar was removed: four cycles, zero working outputs

A live check after the best-effort fix returned **HTTP 200** with an **empty
body** and **no `.json`** for the run — while the PDF was written correctly.
The sidecar had now been broken in four separate ways (§10.0.15–10.0.18) and had
never once produced a valid file.

**Decision: delete it.** That is a judgement, so here is the reasoning.

| The sidecar would have held | Already available from |
|---|---|
| business name | the filename, slugged |
| timestamp | the filename (UTC) |
| review count | the filename (`n`) |
| per-class percentages | the filename (`pos` / `neu` / `neg`) |
| net score | the filename (`net`) |
| the insight list | the rendered PDF |
| low-confidence count | the only unique field — and a derived number the PDF already displays |

So one field was unique, and it was already visible. Everything else was
duplication.

The filename is also the better interface. Sorting the folder sorts by date,
and `ls` shows the statistics without opening anything:

```
review-pulso__sarisari-store-malate__20260930-125313__n100__pos37__neu26__neg37__net0.pdf
```

A sidecar is one more file per run to keep, move and delete.

**The trade-off, stated plainly:** if a client ever needs the raw insight text
*programmatically*, this has to come back — but it should be built by the same
Code node that builds the report, and it must never be on the critical path to
delivering the PDF.

With the sidecar gone, **every node is on the critical path**, so every node is
strict. That is the correct end state: a tolerance setting on the critical path
is exactly the kind that quietly erodes into hiding real failures. The
resilience checks in `19_validate_node_params.py` now assert that *no* node
carries an `onError` override, so that cannot happen by accident.

**The general lesson.** I added the sidecar as a nicety, it never worked, and
repairing it consumed more effort than the feature was worth — four cycles,
each one a debugging round trip. The correct move after the second failure was
to ask whether the feature was earning its complexity, not to attempt a third
repair. Scope that grows without a working baseline becomes a liability.

## 10.0.20 The reports were read-only — and the fix is a uid problem, not a mode problem

The operator reported the output PDFs as read-only. Measured precisely:

```
mode=644   owner=uid 1000 (UNKNOWN)   group=gid 1000
n8n creates 666, container umask 022 turns that into 644
host user is uid 1001 -> "other" -> r-x, no write
```

And the folder itself is 777, so the reachable operations are:

| operation | works? | why |
|---|---|---|
| open / copy the PDF | YES | 644 gives other `r` |
| delete it | YES | needs *directory* write, not file ownership |
| rename it | YES | same |
| create your own file | YES | directory is 777 |
| **edit the PDF in place** | **NO** | needs file write, and you are not the owner |

So the complaint is real but narrower than "read-only", and only the in-place
edit is actually blocked.

**The obvious fix does not work, which is the useful part.** A first attempt
ran `chmod -R` and `find -exec chmod` as the host user and reported success
while changing nothing. **Only the owner of a file or root may chmod it.** The
reports belong to uid 1000; the operator is 1001. So the script could not fix
the files it was written to fix, and it said it had.

That script now refuses to lie: it checks `id -u`, warns when not root, and
counts successes and failures separately.

**Two real fixes now documented:**

1. **Zero risk, no compose change** — a **ROOT** crontab entry:
   ```
   sudo crontab -e
   */5 * * * * /bin/bash .../21_fix_report_permissions.sh >/dev/null 2>&1
   ```
   It must be the *root* crontab, for exactly the ownership reason above. A
   user crontab cannot chmod these files, which is the mistake the first
   version of the script was.

2. **The clean fix, left DISABLED and commented out** in `docker-compose.yml`:
   ```yaml
   command: ["sh", "-c", "umask 000 && exec n8n"]
   ```
   so n8n creates files 666 in the first place.

**Why #2 is not enabled.** I have no Docker access from this session, so I
cannot execute it to confirm n8n still starts. Overriding a container command
risks breaking startup, and a broken n8n is materially worse than a read-only
file. The instruction is written out with its rollback (delete the line,
re-run `docker compose up -d n8n`) so it is a two-minute, reversible test —
but it is a test, and I am not going to hand over a change I could not run and
describe as if I had.

## 10.5 DECISION: form access — shared secret, not Basic Auth

The source doc specifies `authentication: "basicAuth"`. That was **overridden**.
This was flagged for a decision three times before it was settled, so the
reasoning is recorded rather than just the outcome.

**The decision:** `authentication: none` plus a 128-bit unguessable path
segment. Knowing the URL is the credential.

```
https://<your-n8n>/form/review-pulso/3BAC149F67F9B9ED6E17800090BDF7D5
```

**Why:**

1. **The trust model does not need per-client identity.** The report is
   delivered to *our* Telegram, not back to whoever submitted the form. There
   is no private customer data flowing back to an anonymous caller, so the main
   thing Basic Auth would protect — the results — is not exposed either way.
2. **Basic Auth has a real ongoing cost.** Issue, rotate and revoke a
   credential for every business you onboard, plus decide what happens when one
   leaves. For an upload-and-get-a-report workflow, that is a lot of
   credential churn to protect something that is not at risk.
3. **The failure mode of a leaked link is cheap.** A stranger who obtains the
   link can upload a CSV, which costs one model run and one Telegram message.
   That is a nuisance, not a breach. Contrast: a leaked Telegram bot token
   would let a stranger read and *send* on that bot, which is worse and is the
   credential that actually deserves care.

**What this honestly is, stated plainly: obscurity, not authentication.** The
link is the secret, so anyone who obtains it — a forwarded email, a shared
browser history, a screenshot, **n8n's own execution log, which records the
full request URL** — can upload.

**Therefore, and this is the important part:**

- It is adequate for a LAN-bound tool that you hand to a handful of clients.
- It is **not** adequate if n8n is ever exposed to the public internet. n8n is
  bound to `0.0.0.0:5678`, so it is already reachable by everything on your
  network.
- Before any public exposure, switch to real auth. The steps are in the
  generator's comments and in §10.6, and it is a one-line change plus a
  credential per client.

**Rotating the secret** is free and instant: change `FORM_PATH_SECRET` in
`05_generate_workflow_json.py`, re-run it, re-import. No client data is
affected — this secret gates access, it does not encrypt anything.

### 10.6 How to switch to Basic Auth later

1. In `05_generate_workflow_json.py`, set `authentication: "basicAuth"` and
   `formPath` back to just `"review-pulso"`.
2. Re-run the generator and re-import the JSON.
3. n8n UI → **Settings → Credentials → Add credential → Basic Auth**, one per
   client. Pick the right one in the Form Trigger node.
4. Distribute the credentials however you distribute URLs today.

### 10.7 A fourth issue, fixed but worth knowing about

The doc's Node 2b fallback CSV parser splits on `,`:

```javascript
const cols = l.split(',');
```

A quoted review containing a comma — `"Masarap, mura, at sulit!"` — splits in
the wrong place. Worse, in a multi-column CSV it can shift the column index
entirely, so the parser silently reads the **wrong column** as the review.

A quote-aware replacement is in `snippets/node2b_quote_aware_csv_parser.js`.
**Node 2b is not wired in as the default** — the `Extract From File` node
handles quoting correctly and is the primary path. Use the fallback only if Node
2 fails on your n8n version.

#### The bug I introduced while fixing that bug

Worth recording, because the test found it and the code looked correct on
inspection. My first version had a two-stage parse: `splitRows` to find line
boundaries, then `splitFields` to split each line on commas. `splitRows` **consumed**
the quote characters as it walked past them:

```javascript
} else if (ch === '"') {
  inQuotes = true;        // quote seen, but NOT appended to `cur`
}
```

So by the time `splitFields` ran, the line had no quotes left in it. With no
quotes to respect, `splitFields` fell back to naive comma splitting — producing
byte-for-byte the corruption the file existed to prevent.

The first test run was **11 passed, 15 failed** and the failures were the exact
ones that mattered: `"Masarap, mura, at sulit na sulit!"` came back as
`"Masarap"`.

This is the strongest argument in the whole build for writing the test rather
than eyeballing the parser. The code *looked* right. The fix was to make
`splitRows` preserve quotes and toggle state without consuming them, and to
document in the function that quote removal is `splitFields`' job alone.

After the fix: **26 passed, 0 failed**, covering embedded commas, escaped
`""` quotes, literal newlines inside quoted fields, CRLF endings, a UTF-8 BOM
from Excel, nine column-name aliases, a substring fallback, and three error
paths.

the rendered report showed:

1. **`1. 1. Address the leading complaint directly - ...`** — the
   recommendations are an `<ol>`, so the browser already numbers each `<li>`.
   The doc's template *also* injects `<b>${i+1}.</b>`. Two numberings.
2. **The donut's "NET SCORE" caption overflowed onto the coloured ring.** When
   the donut was shrunk from 40mm to 30mm to save vertical space, the caption
   font was not reduced with it, so the text became wider than the white hole.

Neither is a substring problem. The first is an HTML-semantics bug and the
second is pure geometry. Both were found by rendering the page and *looking at

defects are visible rather than inferred.

`14_visual_check_full.png` in this directory is the fixed report.

**(c) Fitting it on one page — measured, and a measurement error of my own.**

The naive fix (card cap 5 → 3) changed nothing for the 5-row test CSV, because
that input has only 2 positive and 2 negative reviews: a cap of 3 and a cap of
5 render identically. The page was overfull for reasons unrelated to card
count.

Measuring per-section with headless Chrome showed the real budget:

| Section | Height |
|---|---|
| header | 34.0mm |
| KPIs | 18.4mm |
| grid (donut + gauge + insights) | 111.3mm |
| &nbsp;&nbsp;— of which the insights list | **74.5mm** |
| 4 comment cards | 84.0mm |
| recommendations | 35.1mm |
| footer | 5.7mm |
| page padding | 26.0mm |
| **total** | **~443mm vs 297mm available** |

**Then I got my own measurement wrong twice.** A probe using
`element.scrollHeight` reported "18mm over", then "14mm over" — but
`.page { min-height: 297mm }` **clamps `scrollHeight` from below**, so once the
content fitted, the probe could no longer detect anything and was reporting an
artefact of the clamp. Measuring the true content extent (bottom of the last
child, relative to the content box) gave 267mm, i.e. already 30mm *under* A4.

A measurement that silently stops measuring is worse than no measurement. The
probe now measures the last child's offsetTop + offsetHeight.

**Final layout, and one design change worth calling out.** Shrinking type was
the easy way to save space, but 8.2pt body text is unpleasant to read in print
and the margin was thin. Instead the two card groups were moved **side by side**
into a two-column flex row. That costs 3 rows of cards instead of 6 — roughly
40mm — which is enough to keep the body at 9.2pt.

| Case | Height | Headroom |
|---|---|---|
| 5-row test CSV | 256.1mm | 40.9mm |
| Worst case (6 negative + 3 positive, 6 insights) | 283.9mm | 13.1mm |

Both render as **one page**. `13_fit_one_page.py` measures this and also
renders a stress case, specifically because the 5-row CSV does not exercise the
card cap on both sides.

Known cosmetic characteristic, not a bug: the "Sentiment mix" panel has
whitespace at the bottom, because the two panels are flex siblings and stretch
to the height of the taller one (the gauge + insights column).

**(d) A check that could not see the failure it claimed to cover.** The smoke
test's T6 asserted A4 portrait and passed — while the document was **two**
pages. A 2-page document is still A4, so the check was structurally incapable
of detecting the violation. Page count is now asserted too.

And the first version of that new check was also wrong: `grep -o '/Type */Page[^s]'`
looks like it counts pages and **silently returns 0**, because the `/Type /Page`
token sits at the end of a line and grep cannot match across a newline. It
reported 0 pages for a document that had 1. Now counted with `python3`, and the
expression was verified non-vacuous by rendering a deliberately over-tall
document and confirming it reports 2.

**(e) A false failure in my own smoke test.** T2 reported:

```
[FAIL] port 8000 IS published - the doc's section 9 says it must not be
[FAIL] port 3000 IS published
```

**Both were wrong. The ports were never published.** Verified directly from the
host: `connect to 127.0.0.1:8000` and `:3000` both return *connection refused*,
while `:5678` connects fine.

The cause was my detection logic, not the stack:

```bash
docker compose port tagasenti 8000 || docker compose port gotenberg 8000
```

This Compose version **exits 0 even when nothing is published**, so
`>/dev/null 2>&1` discarded the (empty) output and the `||` chain reported
success. A test that cries "the security requirement is violated" when the
requirement is satisfied is worse than no test at all.

Replaced with two independent checks that cannot give a false positive:

1. `docker inspect .HostConfig.PortBindings` — the authoritative field, `{}` or
   `null` when nothing is published.
2. An actual TCP connect from the host — the strongest evidence, because it
   tests the property we care about (reachability) rather than a JSON field.

Plus a **negative control**: port 5678 *is* published, so the same probe must
*succeed* there. Without that, T2 would "pass" even if the probe were broken
and could never succeed — the same class of error as the one it just made.

## 12.1 Build-time environment note (why the agent could not run Docker)

The agent's own tool session never acquired the `docker` group, so every Docker
command had to be run by the operator. The cause is worth recording precisely,
because the obvious fixes do not work:

```
/etc/group  modified  19:02:16   ← usermod -aG docker jjjarder
opencode    started   19:10:56   ← AFTER the usermod, but still stale
agent /proc Groups: 4 20 24 27 30 46 122 134 999 1001   ← gid 994 absent
```

opencode restarted *after* the group change, so a naive reading says it should
have worked. It did not, because **a process inherits its supplementary groups
from whatever created it** — and that is the terminal emulator, whose parent is
the desktop session (gnome-shell/GDM) that logged in at 16:12, long before the
change.

Consequences, both of which cost time:

- **Resetting the terminal does not help.** `bash` inherits from a parent that
  never had the group. Only a *full desktop logout* refreshes session
  credentials.
- **`sudo docker` works as a workaround** and is what the operator used, but the
  agent cannot supply a password, so `09_smoke_test.sh` must be invoked as
  `sudo bash ...` for its internal `docker compose` calls to succeed.

The alternative — launching opencode from inside a `newgrp docker` shell — does
give the agent access, at the cost of making `docker` the primary group for
files created in that session.

## 14. Telegram setup — CANCELLED, superseded

**No longer used.** At the operator's request the delivery step was changed from

### 14.0 How delivery works now

```
Node 6 (Gotenberg)  -> binary 'data'  (the PDF)
Node 7 (Filename)   -> sanitises business_name, passes the PDF through,
                       builds a JSON sidecar
Node 8 (Save PDF)   -> writes downloads/<name>.pdf
Node 9 (Save Stats) -> writes downloads/<name>.json
```

The n8n `Read/Write Files from Disk` node in `write` operation resolves relative
paths against `N8N_USER_FOLDER` (default `~/.n8n-files`), so `downloads/x.pdf`
lands at `/home/node/.n8n-files/downloads/x.pdf`, which the compose file maps to
`~/Downloads/review-pulso/` on the host.

Filename format, so the folder is self-describing without opening anything:

```
review-pulso__<business>__<UTC timestamp>__n<count>__pos<p>__neu<u>__neg<g>__net<score>.pdf
```

### 14.0.1 The security consequence of this change

This is the one thing to genuinely think about before deploying. With Telegram,
the filename was fixed by us and a hostile uploader could burn some CPU. **Writing
to disk makes the filename partly client-controlled**, because it is derived from
`business_name` — a form field anyone holding the shared link can set. That is a
path-traversal vector: a value like `../../../../etc/cron.d/x` would try to write
outside the downloads folder.

Mitigations implemented in Node 7, verified by `12_test_filename_logic.js`
(46 assertions):

- `business_name` is slugified to `[a-z0-9-]`, which *structurally* cannot
  contain `/`, `\`, `.` or a null byte.
- The assembled name is then asserted against a strict allowlist regex, so if the
  slug function is ever changed, the workflow fails loudly instead of writing
  somewhere unexpected.
- Length is capped, and a UTC timestamp prevents collisions and overwrites.
- The `downloads/` directory prefix is a **literal in the write node**, not part
  of the interpolated value, so client input cannot influence the directory at
  all.

Residual risk, stated plainly: a shared-link uploader can still cause **repeated
writes** to that folder. That is a disk-fill nuisance, not a data leak, and it is
not solvable inside the workflow — use a cron on the host to prune old reports.

### 14.0.2 One thing NOT verified

n8n's `readWriteFile` path resolution **could not be tested**, because it needs a
running n8n. The relative-path behaviour above is from n8n's documentation, not
from execution. After `docker compose up -d`, confirm the PDF actually appears in
`~/Downloads/review-pulso/`, and check `docker compose logs n8n` for the resolved
absolute path. If it lands somewhere unexpected, set `N8N_USER_FOLDER`

## 19. Reproducing this build's conclusions

The two findings that matter most are cheap to re-verify on other hardware:

```bash
# 1. The model is correct and the label order matches (30 seconds)
python3 agent_journal/01_local_onnx_verification.py

# 2. Throughput, and therefore your upload cap (run detached, ~4 min)
nohup python3 -u agent_journal/08_measure_token_throughput.py > 08.log 2>&1 &
tail -f 08.log
```

The durable finding is not the absolute number — it is that **throughput per
review depends heavily on review length**, so any capacity figure is only valid
for the review length it was measured at. The doc's figure was measured on 15-token
test strings; real reviews are 3–9× longer.

### 20.1 The healthcheck that was always wrong

```yaml
test: ["CMD", "wget", "-qO-", "http://localhost/"]     # wrong
test: ["CMD", "wget", "-qO-", "http://127.0.0.1/"]     # right
```

Inside a container, `localhost` resolves to `::1` first. nginx listens only on
IPv4 `0.0.0.0:80`. Confirmed directly: `wget 127.0.0.1` succeeded, `wget [::1]`
and `wget localhost` both returned "Connection refused". The container was
healthy the entire time.

### 20.2 My own documentation was wrong

`ORCHESTRATION.md` claimed a worst case of "12.8 rev/s, so cap < 768". That
figure came from a run **with a misconfigured tokenizer**, before `tagasenti/`
was populated correctly. Grepping the repository found `12.8` in exactly one
place: my own document.

Four measurements were taken instead, and they disagree:

| Measurement | Rate |
|---|---|
| `01` direct ONNX, short reviews | 39.0 rev/s |
| `02` via `run_many()`, same reviews | 12.4 rev/s |
| `02` via `run_many()`, ~112-token reviews | 1.5 rev/s (3.1 unloaded) |
| `04` direct ONNX, all rows padded to 128 tok | 2.7 rev/s |

The 3x gap between `01` and `02` on identical input is **unexplained** and is
recorded as such rather than given a convenient story. The numbers are also
load-dependent: the same benchmark ran at half speed while this machine was at
load average 4.72.

The cap was re-derived against the timeout the implementation actually has -
Node 4's 600s - and 1000 rows at ~112 tokens measures 326s unloaded. It was
655s under load, which would have timed out. That limit is now documented
rather than glossed.

### 20.3 The defect I am most glad I found

Node 3 built this message:

```
Too many reviews: 1100 unique rows found, but the cap is 1000.
Split the CSV into files of 1000 rows or fewer ...
```

and then `throw` it. **A throw aborts the execution, so `Respond to Webhook`
never runs.** n8n returned `{"message":"Error in workflow"}`, HTTP 500. The
message was constructed in one node and discarded by the framework in the next.

The same pattern silently swallowed the "no usable reviews found" error.

The generalisable rule, now in `ORCHESTRATION.md`: **in n8n, a `throw` is
invisible to your own Respond node.** Checks whose messages are meant for humans
need a routing path.

Fixed with two nodes - an IF and a 400 responder. The IF's parameter shape was
read out of the installed n8n 2.40.7 rather than guessed, because a malformed
condition does not error loudly; it just routes everything one way.

Two throws were deliberately left alone, and the distinction matters:

- **Node 5** - tagasenti returned a different result count than reviews sent.
  That is a broken contract between our own services. It belongs in the
  operator's log; a 4xx would mislabel it as the client's fault.
- **Node 7** - the filename safety assertion. It must block the write to
  prevent path traversal. Security controls fail closed.
